# 0024. 자동 질문의 데이터 도구와 인자는 LLM이 고르고 서버가 검증한다

- 상태: 제안
- 날짜: 2026-11-12
- 결정자: 윤영채
- 관련: [계획](../plans/2026-11-12-llm-tool-selection.md), [통합 답변 계약](../specs/integrated-answer.md), [ADR 0015](0015-optional-model-workflow-skills.md), [ADR 0012](0012-openai-compatible-chat-completions.md)

## 배경

`/api/ask`의 자동 질문은 정규식 처리기를 순서대로 시도해 작업을 정하고, 각 처리기가 질문 원문에서 선박·기간·조건을 다시 정규식으로 추출한다. LLM은 모든 규칙이 거절한 뒤에만 action 하나를 JSON으로 고르는 보조 분류기다(`question_router.model_route`). 낯선 표현은 규칙에서 빠지고, 모델 분류는 작업 이름만 정해 효과가 작다([질문 표현 다양성 계획](../plans/2026-11-11-question-routing-coverage.md)).

[ADR 0015](0015-optional-model-workflow-skills.md)는 "모델은 임의 Tool·SQL·scope를 실행하지 않는다"고 정했다. 이번 결정은 이 원칙 중 "모델이 도구와 범위를 고르지 않는다"는 부분을 바꾼다.

## 결정

1. **문서 검색은 모든 자동 질문에서 항상 실행한다.** 모델이 무엇을 고르든 답변의 문서 근거를 확보한다. 라우팅 모델 입력에는 검색 본문을 넣지 않는다.
2. **모델은 추가로 실행할 데이터 도구와 인자를 OpenAI 호환 tool calling으로 고른다.** 0개 이상, 상한 내에서 고른다. 도구 정의는 서버의 단일 등록부(`backend/api/tool_registry.py`)에서 만든다.
3. **서버는 실행 전에 모든 호출을 검증한다.**
   - 도구 이름은 등록부 allowlist에 있어야 한다. 쓰기·관리·인증 기능과 서버 전용 Tool API(`/api/maritime-data/*`)는 등록하지 않는다.
   - 인자는 Pydantic 스키마(추가 필드 거절)를 통과해야 한다.
   - 선박·문서·항구는 모델이 낸 원문 표기를 등록 목록·열람 권한·항구 카탈로그와 대조해 서버가 식별자로 바꾼다. 모델은 식별자를 직접 정하지 않는다.
   - 날짜는 모델이 원문 기간 표현을 넘기고 기존 해석기(`question_intent.date_slots`)가 ISO 날짜로 바꾼다.
   - 사용자 확인이 필요한 값(MRV 참고값 동의 `reference_ack`)은 모델이 설정할 수 없다.
4. **모델은 답변 문장을 직접 만들지 않는다.** 답변 생성은 기존처럼 검색 근거와 도구 결과의 인용 검증을 통과해야 한다.
5. **모델이 없으면 자동 질문을 처리하지 않는다.** 모델 미설정은 `MODEL_NOT_CONFIGURED` 오류, 호출 실패·잘못된 도구 호출·검증 실패는 되묻기(`MODEL_ROUTING_UNAVAILABLE`)로 응답한다. 답변 방식 선택(`mode`)은 제거한다.
6. **기존 정규식 경로는 legacy로 남긴다.** 서버 환경변수로 명시했을 때만 사용하며 기본 경로의 대체 수단으로 자동 사용하지 않는다.
7. **응답에 사용한 도구를 기록한다.** 서버가 검증한 도구 이름·인자·결과 상태·소요 시간을 응답과 감사 기록에 남기고 화면에 표시한다. 모델의 원시 응답은 저장하지 않는다.

이 ADR이 채택되면 ADR 0015의 상태를 `대체됨(0024, 스킬 카탈로그와 고정 서버 실행기 결정은 계승)`으로 바꾼다.

## 검토한 대안

| 대안 | 장점 | 단점 / 채택하지 않은 이유 |
|---|---|---|
| 현행 유지 (규칙 우선, 모델은 action 분류만) | 모델 없이 동작, 재현성 높음 | 새 표현마다 정규식 추가 필요, 모델 효과 작음 |
| 모델이 action만 고르고 인자는 규칙 추출 | 인자 오류 위험 작음 | 인자 추출이 그대로 정규식에 묶여 표현 다양성 문제가 남음 |
| 문서 검색도 모델이 고르는 도구로 둠 | 구조 단순, 표시가 모델 선택과 일치 | 모델이 잘못 고르면 문서 근거가 빠짐 |
| 모델 실패 시 legacy 규칙으로 자동 대체 | 가용성 높음 | 두 경로의 결과가 섞여 동작 예측·검증이 어려움 |
| 모델이 상대 날짜를 ISO로 변환 | 표현 범위 넓음 | 작은 모델의 날짜 계산 오류 위험 |

## 결과

- 좋아지는 점: 정규식에 없는 표현도 처리할 수 있다. 모든 답변에 문서 근거가 붙는다. 사용한 도구를 사용자가 확인할 수 있다. 도구 목록이 한곳에서 관리된다.
- 감수하는 점: 모델이 없는 환경에서는 자동 질문을 쓸 수 없다. 응답 시간과 모델 호출 비용이 늘어난다. 도구 선택 정확도가 모델 성능에 의존한다(기존 Qwen2.5 3B 분류 실측 5건 중 3건 일치).
- 이 결정 때문에 지켜야 할 규칙:
  - 새 도구는 등록부에만 추가하며, 읽기 전용이고 사용자 권한 검사를 통과하는 실행 함수만 등록한다.
  - 모델이 낸 값은 검증 전까지 신뢰하지 않으며 SQL·식별자·수치로 직접 사용하지 않는다.
  - 실제 모델 평가 결과와 모의 모델 테스트 결과를 구분해 기록한다.
